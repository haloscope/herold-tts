# AAR 2026-08-03: v0.4.0 — API expansion, demo web service and CPU profile

## Objective

Complete the last two roadmap items: replace fire-and-forget REST calls with trackable jobs and accessible results, and provide an example web service. Also expose the tested but not yet wired CPU image through a Docker Compose profile.

## What happened

- Confirmed design decisions (HTML demo within FastAPI, job status and file endpoints, CPU Compose profile), as documented in [ADR 0002](../adr/0002-integrierte-demo-und-inmemory-jobs.md).
- `herold/api.py`: in-memory job registry, `GET /api/jobs/{id}`, `GET /api/files[/{dir}/{name}]` with reused `convert.validate_filename_stem`, static mount `/demo` and redirect from `/` to `/demo/`.
- `herold/static/index.html`: self-contained **German-language demo at the time** (render → poll → listen → convert → download), calling only the public API. The interface was subsequently localized into English in v0.4.4.
- `docker-compose.yml`: enabled the CPU service under `profiles: ["cpu"]`, port 8001.
- Tests: added 13 API cases in `tests/test_api.py` and `httpx` for testing. Set up a local environment on the Mac using Homebrew `python@3.12` and `.venv`; all 41 tests passed.
- Documentation: corrected quick starts and documented new endpoints in `DEPLOYMENT.md`; updated README, CLAUDE.md, v0.4.0 changelog and ADR 0002.

## Lessons learned

- The Mac previously had Python 3.9, which was too old for torch ≥2.9. Homebrew Python 3.12 and `.venv` allow local mocked tests described in CLAUDE.md, without loading models.
- `docs/DEPLOYMENT.md` retained several examples from before restructuring (`cd work`, Dockerfile at repository root, volume paths without `data/`). When changing documentation, examine neighboring examples rather than only the immediately affected section.
- FastAPI's `on_event` was deprecated (test-suite warnings). The v0.3.x implementation was deliberately left untouched; converting to lifespan handlers is a later task.

## Addendum: Partial tests on the Mac (same day)

- Stages 1 (pytest) and 2 (mocked demo) passed. Stage 3 built the CPU image **natively for linux/arm64** (around 70 minutes; all dependencies had aarch64 wheels). Container smoke checks passed (`/api/status` reporting `device=cpu`, demo page, file listing, and 404/400 guards). Aborted before the actual render test due to heavy system load; removed the container, both images, and 13.4 GB of build cache afterward.
- Two findings were fixed in v0.4.1: unnecessary CUDA dependencies in the CPU image (default PyTorch wheels) and a health check importing the full ML stack on every probe (false `unhealthy` on slower hosts).
- Additional finding: `docker compose --profile cpu up` also tries to start the default GPU service, because services without a profile always run. On hosts without an NVIDIA runtime, use `docker compose --profile cpu up -d herold-tts-cpu` instead.
- The second build attempt with the v0.4.1 fixes was also aborted. The root cause was the Mac's **8 GB RAM**: the Docker VM plus build/venv I/O caused memory pressure and swapping, making trivial build steps up to 30 times slower. Do not run Docker builds or models on this Mac. It is suitable for editing, mocked pytest runs in `.venv`, and Git; run containers on the test machine.

## Open and follow-up items

- [ ] End-to-end verification on the test machine using the **v0.4.1 images** after rebuilding: GPU (`docker compose build && up`, demo on port 8000) and CPU (`--profile cpu up -d herold-tts-cpu`, port 8001), including render and conversion in the demo. Also verify cache persistence across rebuilds and `healthy` container status after the health-check fix.
- [x] CI pipeline (v0.4.2, ADR 0003) enabled, with the first fully passing run on 2026-08-04. Two infrastructure issues arose on Overmind/Dokploy:
  1. **Large registry layer pushes failed exactly after 60 seconds with HTTP 504.** Dokploy's Traefik v3 sits in front of GitLab and terminates TLS; GitLab itself publishes port 80. `respondingTimeouts.readTimeout=60s` was a *total request read* timeout, not an inactivity timeout. Fixed in `/etc/dokploy/traefik/traefik.yml` under `entryPoints.websecure` with `transport.respondingTimeouts.readTimeout: 0s`, followed by `docker restart dokploy-traefik`. An earlier `registry_nginx` adjustment in `gitlab.rb` did not help; internal nginx measured inactivity and was not the failing component.
  2. Manual pushes/pulls as the user returned `denied`, including for small layers (a permissions issue, not a timeout). The CI job token could push normally. A replacement personal access token with `read_registry` and `write_registry` was under evaluation.
- [x] Investigated the initial `build-gpu` failure on 2026-08-03: the two large layers (virtualenv ~8 GB and CUDA base) consistently failed with HTTP 504 after 60 seconds. An initial hypothesis identified registry-front nginx inside GitLab Omnibus (running as a Compose stack). Server-side settings were tried in `gitlab.rb`: `registry_nginx['client_max_body_size']='0'`, `proxy_read_timeout` and `proxy_send_timeout` set to 3600, followed by a stack restart. The later investigation above identified Traefik's total read timeout as the effective root cause. General lesson: uploading a layer longer than the proxy's timeout can fail even while small layers succeed.
- [ ] Later options: replace `on_event` with lifespan handlers; introduce a persistent queue only for multi-instance needs (ADR 0002). Devcontainer work was deferred on 2026-08-03 and should be reconsidered if the team grows or CI expands.
