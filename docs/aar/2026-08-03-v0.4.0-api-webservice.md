# AAR 2026-08-03: v0.4.0 — API-Ausbau, Demo-Webservice, CPU-Profil

## Ziel

Die letzten beiden Roadmap-Punkte umsetzen: die REST-API von Fire-and-forget auf nachvollziehbare
Jobs mit Ergebnis-Zugriff heben und einen exemplarischen Webservice bauen; dazu die getestete,
aber nicht verdrahtete CPU-Variante als Compose-Profil nutzbar machen.

## Was geschah

- Nutzerentscheidungen eingeholt (HTML-Demo in der FastAPI-App, Job-Status + Datei-Endpoints,
  CPU als Compose-Profil) → Umsetzung gemäß [ADR 0002](../adr/0002-integrierte-demo-und-inmemory-jobs.md)
- `herold/api.py`: In-Memory-Job-Registry, `GET /api/jobs/{id}`, `GET /api/files[/{dir}/{name}]`
  (Wiederverwendung von `convert.validate_filename_stem`), StaticFiles-Mount `/demo`, `/` → `/demo/`
- `herold/static/index.html`: selbst-enthaltene deutsche Demo-Seite (rendern → pollen → anhören →
  konvertieren → laden), nutzt nur die öffentliche API
- `docker-compose.yml`: CPU-Service aktiviert hinter `profiles: ["cpu"]`, Port 8001
- Tests: `tests/test_api.py` (13 Fälle), `httpx` als Test-Abhängigkeit; erstmals lokale
  Test-Umgebung auf dem Mac aufgesetzt (Homebrew `python@3.12` + `.venv`) — 41/41 grün
- Doku: DEPLOYMENT.md (Quickstarts korrigiert, neue Endpoints), README, CLAUDE.md, CHANGELOG
  v0.4.0, ADR 0002

## Gelernt

- Der Mac hatte nur Python 3.9 (zu alt für torch ≥2.9) — mit Homebrew-`python@3.12` + `.venv`
  läuft der in CLAUDE.md dokumentierte Test-Workflow jetzt auch lokal; Modell bleibt gemockt.
- `docs/DEPLOYMENT.md` enthielt noch mehrere Reste aus der Vor-Restrukturierungs-Zeit
  (`cd work`, Root-`Dockerfile`, Volume-Pfade ohne `data/`) — bei Doku-Änderungen lohnt der
  Blick auf die Beispiele im Umfeld, nicht nur auf den direkt betroffenen Abschnitt.
- FastAPIs `on_event` ist deprecated (Warnungen in der Testsuite); Bestand aus v0.3.x, bewusst
  nicht angefasst — Kandidat für einen späteren Lifespan-Umbau.

## Nachtrag: Teiltest auf dem Mac (gleicher Tag)

- Stufe 1 (pytest) und Stufe 2 (Demo-UI mit gemocktem Modell) erfolgreich; Stufe 3:
  CPU-Image baute **nativ für linux/arm64** (~70 min, alle Deps mit aarch64-Wheels),
  Smoke-Check gegen den Container grün (`/api/status` device=cpu, Demo-Seite, Datei-Listing,
  404/400-Guards). Vor dem Render-Test wegen starker Systemlast abgebrochen und komplett
  zurückgebaut (Container, beide Images, 13,4 GB Build-Cache).
- Zwei Befunde, gefixt in v0.4.1: CUDA-Ballast im CPU-Image (Standard-torch-Wheels) und
  Healthcheck, der pro Probe den ML-Stack importierte (false-unhealthy auf langsamen Hosts).
- Nebenbefund am Rande: `docker compose --profile cpu up` versucht auch den GPU-Service zu
  starten (profillose Services laufen immer mit) — auf Hosts ohne NVIDIA-Runtime gezielt
  `up -d herold-tts-cpu` verwenden.
- Zweiter Build-Versuch (mit v0.4.1-Fix) ebenfalls abgebrochen: Grundursache aller
  Mac-Probleme ist, dass das Gerät nur **8 GB RAM** hat — Docker-VM + Build/venv-I/O führt
  in Speichernot und Swapping (triviale Build-Schritte 30× langsamer). Konsequenz: Docker-
  Builds und Modell-Läufe auf diesem Mac generell vermeiden; er taugt für Editieren, pytest
  (.venv) und den gemockten API-Lauf — alles Containerisierte gehört auf die Testmaschine.
